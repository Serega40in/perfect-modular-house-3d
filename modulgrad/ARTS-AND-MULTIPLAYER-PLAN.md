# Модульград — визуальный пакет и промты для генерации

Цель: создать согласованный набор графики для браузерной 3D-игры ЛенКаркасМодуль. Визуальный стиль — тёплый премиальный архитектурный симулятор, реалистичные материалы, чистая композиция, естественные зелёные акценты, без текста и водяных знаков.

## Важно: как использовать существующие арты

Существующие файлы в `modulgrad/assets/` включают одиночные дома, изображение нескольких домов, строительную сцену, модуль в разрезе, стеновой разрез и ландшафт у воды. Изображение нескольких домов нельзя назначать миниатюрой одного дома 8×3. Карточки каталога должны показывать одиночный дом похожего масштаба и формы. Пока нет точного рендера для конкретного SKU, использовать наиболее близкий одиночный референс и помечать его как иллюстрацию, не как точную комплектацию.

## Общие требования к генерации

- Для карточек домов: 1:1 или 4:3, дом целиком в кадре, единый изометрический ракурс 3/4, нейтральный светлый фон, без текста, людей и логотипов.
- Для сцен: 16:9, архитектурная визуализация высокого качества, понятный фокус и свободное место для UI.
- Для иконок: 1:1, простой силуэт, прозрачный фон PNG, читаемость в 24–64 px.
- Для игровых объектов/персонажей: прозрачный фон PNG, полный объект/персонаж, без обрезанных конечностей, единый свет.
- Не добавлять надписи, псевдотекст, водяные знаки, дополнительные окна/двери, невозможные свесы или случайные модули.
- Сохранять узнаваемость реальных домов компании по референсным изображениям. Не придумывать коммерческие характеристики.
- Предпочтительный формат: WebP для крупных сцен, PNG для прозрачных иконок/персонажей; JPEG/WebP для карточек.

## Проверка перед подключением

1. Сверить картинку с реальным SKU/размером; особенно соблюдать пропорции 6×3 и 8×3.
2. Не назначать коллаж с несколькими домами карточкой одного дома.
3. Проверить все изображения в каталоге, на мобильном экране и при медленной загрузке.
4. Сохранить исходные файлы; новые версии добавлять под новыми именами.
5. Коммерческие цены, сроки и комплектации сверять с компанией до публикации.

## План продукта: мультиплеер и реальные заказы

- Сначала: гостевой кабинет и облачное сохранение проектов.
- Затем: публикация планировки, ссылка для просмотра, дублирование проекта, лайки/комментарии и жалобы.
- Далее: профили игроков, друзья, совместное редактирование с разрешениями, версии/история изменений.
- Интеграция с реальной компанией: кнопка «Запросить расчёт», отправка проекта и контактных данных только с согласия пользователя, заявка в CRM/почту через серверную функцию.
- Не обещать точную смету по игровой модели: до подтверждения специалистом она остаётся предварительным расчётом.

## Архитектурные рекомендации

GitHub Pages оставляем фронтендом. Для аккаунтов, облачных проектов, сообщества и заявок нужен серверный слой: Supabase Auth + Postgres + Storage + Row Level Security. Не помещать service-role ключ в браузер. Проект хранить в версионируемом JSON с валидацией, владельцем, видимостью (private/unlisted/public), временными метками и историей версий. Перед совместным редактированием — права доступа, резервное сохранение, лимиты и модерация.
